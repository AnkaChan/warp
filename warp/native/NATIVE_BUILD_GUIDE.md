# Warp Native C++/CUDA Code Guide

## Directory Layout

```
warp/native/
├── cmake/WarpSources.cmake   # CMake include for standalone C++ projects
├── clang/                     # LLVM/Clang JIT compiler integration
├── nanovdb/                   # NanoVDB third-party (sparse volumetric grids)
├── libdevice/                 # CUDA libdevice support
├── *.h                        # Headers (types, math, algorithms)
├── *.cpp                      # CPU implementations
└── *.cu                       # CUDA/GPU implementations
```

## Header Dependency Chain

`builtin.h` is the mega-include. Nearly everything flows through it:

```
builtin.h
├── crt.h              (C runtime: assert, isfinite, isnan, math — defines WP_API)
│   └── cuda_crt.h     (CUDA-specific runtime, conditional on __CUDACC__)
├── vec.h              (vec2/3/4 templates)
│   └── initializer_array.h
├── mat.h              (matrix templates, 5500+ lines)
├── quat.h             (quaternion math)
├── spatial.h          (spatial vectors/transforms)
├── intersect.h        (ray-triangle, ray-box intersection)
│   └── intersect_tri.h
├── intersect_adj.h    (adjoint/gradient intersection for autodiff)
├── array.h            (array_t<T> template — the core data container)
│   └── fabric.h
├── tuple.h
├── mesh.h             (Mesh struct, query functions, 2700 lines)
├── bvh.h              (BVH struct, bounds3, traversal, 590 lines)
├── svd.h
├── hashgrid.h
├── volume.h / texture.h
├── range.h / rand.h / noise.h
├── matnn.h            (neural net matrix ops)
└── tile*.h            (GPU tile/warp-level operations)
```

`warp.h` includes `builtin.h` and declares the entire C API (`wp_*` functions).

## Key Data Structures

### BVH (`bvh.h`)
```cpp
struct BVHPackedNodeHalf {
    float x, y, z;         // bounding box corner
    unsigned int i : 31;   // child index (internal) or primitive range (leaf)
    unsigned int b : 1;    // 1 = leaf node
};

struct BVH {
    BVHPackedNodeHalf* node_lowers;  // packed lower bounds + child/prim info
    BVHPackedNodeHalf* node_uppers;  // packed upper bounds + child/prim info
    int* node_parents;               // parent indices (for bottom-up refit)
    int* node_counts;                // atomic counters for GPU refit
    int* primitive_indices;          // reordered primitive indices
    int* root;                       // pointer to root node index
    vec3* item_lowers;               // original AABB lowers (not owned)
    vec3* item_uppers;               // original AABB uppers (not owned)
    int* item_groups;                // optional group IDs for grouped BVH
    int num_items, num_nodes, num_leaf_nodes, max_nodes, max_depth, leaf_size;
    void* context;                   // CUDA context
};
```

**Leaf encoding**: For leaf nodes, `lower.i` = start index into `primitive_indices`, `upper.i` = end index (exclusive). For internal nodes, `lower.i` = left child, `upper.i` = right child.

**Node ordering**: After construction, leaf nodes are stored at the front of the arrays, internal nodes after. This is important for GPU refit (leaves processed first, then parents via atomic counters).

### Construction Algorithms
- **SAH** (`BVH_CONSTRUCTOR_SAH = 0`): Surface Area Heuristic, CPU only, best quality
- **Median** (`BVH_CONSTRUCTOR_MEDIAN = 1`): Median split, CPU only, faster build
- **LBVH** (`BVH_CONSTRUCTOR_LBVH = 2`): Linear BVH via Morton codes, GPU only (`bvh.cu`)

### Mesh (`mesh.h`)
```cpp
struct Mesh {
    array_t<vec3> points, velocities;
    array_t<int> indices;
    vec3* lowers; vec3* uppers;          // per-triangle AABBs
    SolidAngleProps* solid_angle_props;  // for winding number queries
    int num_points, num_tris;
    BVH bvh;                             // embedded BVH
    void* context;
    float average_edge_length;
};
```

## Compile Definitions

| Define | Meaning |
|--------|---------|
| `WP_ENABLE_CUDA` | 0 or 1 — enables CUDA code paths |
| `WP_ENABLE_CUDA_COMPATIBILITY` | Enhanced CUDA compat (usually 0) |
| `WP_ENABLE_DEBUG` | Debug assertions and checks |
| `WP_ENABLE_MATHDX` | MathDx library support |
| `WP_NO_CRT` | Used by JIT-compiled kernel modules (not for runtime build) |
| `WP_API` | `__declspec(dllexport)` on Windows, `__attribute__((visibility("default")))` on Linux |

## Building as Part of a C++ Project

Use `warp/native/cmake/WarpSources.cmake`:

```cmake
set(WARP_DIR "path/to/warp")
include(${WARP_DIR}/warp/native/cmake/WarpSources.cmake)

# Provides: WARP_CXX_SRCS, WARP_CUDA_SRCS, WARP_INCLUDE_DIR,
#           WARP_COMPILE_DEFINITIONS, WARP_MSVC_OPTIONS,
#           WARP_CUDA_OPTIONS, WARP_CUDA_LINK_LIBS, WARP_CUDA_FOUND
```

### Generator Choice
Use **Visual Studio 17 2022** generator (not Ninja). Ninja may pick up the wrong compiler (e.g. GCC from Strawberry Perl) and fail to find CUDA.

```bash
cmake .. -G "Visual Studio 17 2022" -A x64
cmake --build . --config Release
```

### Visual Studio Gotcha
The VS generator produces broken output paths for CUDA `.cu` files located outside the project tree (`nvcc fatal: A single input file is required`). Workaround: compile CUDA sources as a separate `STATIC` library target, then link it into your executable. Do NOT add `.cu` files directly to `add_executable()`. See `warp/examples/bvh_test/CMakeLists.txt` for a working example.

### MSVC Runtime
The original warp build uses `/MT` (static CRT, non-debug even in Debug). If you need debug CRT, adjust `CMAKE_MSVC_RUNTIME_LIBRARY`.

## C API Entry Points

All public API functions are `extern "C"` with `WP_API` linkage, prefixed `wp_`:
- `wp_init()` — initialize runtime
- `wp_bvh_create_host/device()` — returns uint64_t handle
- `wp_bvh_destroy_host/device()`, `wp_bvh_refit_host/device()`, `wp_bvh_rebuild_host/device()`
- `wp_mesh_create_host/device()`, `wp_mesh_destroy_host/device()`, etc.
- `wp_alloc_host/device()`, `wp_free_host/device()`, `wp_memcpy_*()` — memory management
- `wp_cuda_device_get_count()`, `wp_cuda_device_get_primary_context()`, `wp_cuda_context_set_current()` — CUDA context

Internal C++ API (in `wp` namespace, not exported):
- `bvh_create_host()`, `bvh_destroy_host()` — direct struct manipulation
- `bvh_get_descriptor()`, `bvh_add_descriptor()` — host-side map of device BVH handles

## Descriptor Pattern

Device-side objects (BVH, Mesh, HashGrid) use a descriptor pattern:
1. Build on host or device
2. Store in a `std::map<uint64_t, T>` keyed by pointer address
3. `wp_*_create_device()` returns the device pointer cast to `uint64_t`
4. The host-side map allows querying device object metadata from CPU

## Gotchas & Lessons Learned

### 1. `warp.cpp` #includes other .cpp files
`warp.cpp` lines 865-866 do `#include "bvh.cpp"` and `#include "scan.cpp"`. If you compile those as separate translation units you get LNK2005 duplicate symbol errors for every function in them. The `WarpSources.cmake` already excludes them from `WARP_CXX_SRCS`.

### 2. Visual Studio + CUDA files outside project tree
When `.cu` files live outside the VS project directory (e.g. via absolute paths to `warp/native/`), the VS CUDA build customization generates malformed output paths like `-o bvh_test.dir\Release\/D_/Code/...` which causes `nvcc fatal: A single input file is required`. **Fix**: compile all `.cu` files in a separate `add_library(warp_cuda STATIC ...)` target, not directly in `add_executable()`.

### 3. Ninja picks up wrong compiler on Windows
If Strawberry Perl or MinGW is on PATH, `cmake -G Ninja` may find GCC instead of MSVC, and then CUDA detection fails. **Fix**: always use `-G "Visual Studio 17 2022" -A x64`.

### 4. `scan.cpp` uses undeclared functions
`scan.cpp` calls `wp_alloc_host()`, `wp_free_host()`, `wp_memcpy_h2h()` without including `warp.h` — it only includes `scan.h`. This works in the original build because `warp.cpp` #includes `scan.cpp` after already including `warp.h`. If you ever separate `scan.cpp` into its own translation unit, you'll need to add `#include "warp.h"` to it.

### 5. CUDA link libraries
`warp.cu` uses nvrtc and nvPTXCompiler. You must link against:
- `CUDA::cudart_static`
- `CUDA::cuda_driver`
- `CUDA::nvrtc_static`
- `CUDA::nvrtc_builtins_static`
- `CUDA::nvptxcompiler_static`
- `CUDA::nvJitLink_static` (CUDA 12+)

Missing these causes unresolved externals for `nvrtcCreateProgram`, `nvPTXCompilerCreate`, etc. The `WARP_CUDA_LINK_LIBS` variable in `WarpSources.cmake` provides the full list.

### 6. CUDA separable compilation required
The CUDA static library needs `CUDA_SEPARABLE_COMPILATION ON` and `CUDA_RESOLVE_DEVICE_SYMBOLS ON`, otherwise device-link fails.

### 7. Device BVH descriptor has uninitialized host-side fields
When you create a device BVH via `wp_bvh_create_device()` and read it back via `bvh_get_descriptor()`, some fields like `num_nodes` and `max_depth` may contain garbage because they live in device memory and aren't fully copied back. Only `num_items` and `num_leaf_nodes` are reliable from the host-side descriptor.

### 8. CUDA context must be set before device operations
Before calling any `wp_*_device()` function, you must:
```cpp
void* ctx = wp_cuda_device_get_primary_context(0);  // ordinal 0
wp_cuda_context_set_current(ctx);
```
There is no `wp_cuda_device_primary_context_retain()` — `wp_cuda_device_get_primary_context()` handles it.

### 9. `wp_init(nullptr)` works but warns
Passing `nullptr` to `wp_init()` skips version checking and prints a warning. This is fine for standalone C++ usage where you don't care about Python version matching.

### 10. Don't modify existing warp source files
The user prefers keeping warp source files unmodified. All integration should be additive (new cmake files, new example projects). This keeps the fork cleanly mergeable with upstream.

## File Cross-References

When working on mesh/BVH:
- Query algorithms: `mesh.h` (mesh_query_point, mesh_query_ray, etc.)
- Intersection math: `intersect.h`, `intersect_tri.h`
- Solid angle / winding number: `solid_angle.h`
- BVH traversal stack: hardcoded `BVH_QUERY_STACK_SIZE = 32` (max depth)
- GPU tile operations: `tile_bvh.h`, `tile_mesh.h`
